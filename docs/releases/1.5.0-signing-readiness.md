# GizeCat 1.5.0 signing readiness report

Where code signing stands for the 1.5.0 "Living Companion" release candidate (Windows and Android), what exists in the repository, what is missing, and the exact steps only the owner can take. Derived from the repository on the branch `feature/living-companion`; nothing here was bought, applied for or run.

Status words used on this page:

| Word | Meaning |
|---|---|
| IMPLEMENTED | The code or configuration exists in the repository |
| COMPILED_OR_PACKAGED | It type-checks, builds or packages |
| statically verified | Type-check, lint or read-only review only; nothing executed |
| OWNER-VERIFIED | The owner ran it on real hardware |
| NOT RUN | Nobody ran it |
| REQUIRES_OWNER_CREDENTIALS | Cannot proceed without a credential only the owner can obtain |

## Summary

- **The 1.5.0 Windows installers are unsigned.** No code-signing certificate and no SignPath project exists. Windows will show an "Unknown publisher" style prompt, and SmartScreen or Smart App Control may warn or block (section 1.3).
- **The 1.5.0 Android release APK and AAB are unsigned.** No production keystore exists. Android will not install the unsigned APK, and Google Play will not accept the unsigned AAB (section 2.1).
- **The Android trial APK is signed with the Android debug certificate.** It is a sideload trial with its own application id (`io.github.gizeverse.gizecat.trial`), never a release (section 2.1).
- **Nothing in 1.5.0 has been run.** No test, emulator, simulator or application launch was performed for any 1.5.0 code. The Android 1.4.2 floating cat was OWNER-VERIFIED on one physical Android phone; 1.5.0 changes to it are not.
- **A signature would not change that.** A signature shows who published a file and that it is unchanged. It does not show that the app works, that Google Play approves it, that Windows trusts it, or that it is free of malware.
- **Nothing is published or tagged.** 1.5.0 is a release candidate that the owner reviews and publishes.

Release candidate files (named by the build; hashes are not recorded in repository documentation, and the maintainer fills them in later in `release/1.5.0/SHA256SUMS.txt`):

The names come from `scripts/android-gradle.mjs` (Android) and `nsis.artifactName` in `electron-builder.yml` (Windows). The `-unsigned` names appear because no release key was configured; with a key the same script would name the files `GizeCat-<version>-android.apk` and `.aab`. These files may not exist on your disk until the background build has finished; check `release/1.5.0/`.

The Windows installers have not been checked with `scripts/verify-windows-signature.ps1` for 1.5.0; "unsigned" follows from there being no certificate configured (electron-builder logs that signing is skipped). Run the verifier on the real files before you state their signature state in public.

## 1. Windows

### 1.1 What exists in the repository

| Item | Where | State |
|---|---|---|
| SHA-256-only signing and an RFC 3161 timestamp (DigiCert's public timestamp service, `/td sha256`) | `electron-builder.yml`, `win.signtoolOptions` | IMPLEMENTED. Used only when a certificate is configured; without one electron-builder skips signing and these keys change nothing |
| Local signing with a certificate in the Windows certificate store (token, smart card or cloud HSM), modes `SignExisting` and `Rebuild` | `scripts/sign-windows.ps1` | IMPLEMENTED; NOT RUN. Owner tool; agents never run it |
| Signature verification (Authenticode validity, timestamp, SHA-256 only) and byte comparison of signed against unsigned | `scripts/verify-windows-signature.ps1`, `scripts/compare-signed-pe.mjs` | IMPLEMENTED; they read files and run no installer. Never run on a signed GizeCat file |
| CI signing through SignPath (two rounds, each approved by a person in SignPath) | `.github/workflows/release.yml`, input `windows_signing: signpath`, environment `windows-signing` | IMPLEMENTED; NOT RUN; REQUIRES_OWNER_CREDENTIALS |
| SignPath artifact configurations (reference copies to paste into SignPath) | `.github/signpath/windows-installers.xml`, `windows-app-helper.xml`, `windows-app-helper-and-exe.xml` | IMPLEMENTED; never validated by SignPath |
| Unsigned CI build path | `release.yml`, input `windows_signing: unsigned` | IMPLEMENTED; NOT RUN |
| Other workflows | `.github/workflows/ci.yml` (push, pull request and manual), `installer-check.yml` (manual) | They run tests or install the app; they are not signing paths. The owner's note says GitHub Actions on the private repositories have not started jobs since 2026-10-02 (account billing), so treat CI as absent until a run actually starts |

`release.yml` is manual only (`workflow_dispatch`). The earlier `.pfx` secret route was removed from it: since June 2023 the private key of a publicly trusted code-signing certificate must live in hardware (token, smart card or HSM), so a new certificate cannot be exported as a `.pfx` and stored as a CI secret.

Full route comparison (SignPath Foundation, Certum Open Source Code Signing, other CAs, Azure Artifact Signing, EV, Microsoft Store/MSIX) is in [windows-signing.md](../platforms/windows-signing.md). That research dates from 2026-11-10; prices and eligibility change, so check each provider again.

### 1.2 What is missing

- A code-signing certificate, **or** an accepted SignPath project. Neither exists. Nothing was bought, enrolled in or applied for.
- For SignPath Foundation: the project and signing policy in SignPath, MFA for everyone with access, a published code signing policy page, and the `windows-signing` GitHub environment with its secret and variables.
- For a local certificate: the certificate itself on a token or cloud HSM, and the Windows SDK's `signtool.exe`.
- Any real signing run. Every statement about a signed result is untested until a real certificate or project exists.

### 1.3 Consequences of shipping unsigned (stated without exaggeration)

- The installers have no Authenticode signature. Windows shows no verified publisher for them ("Unknown publisher" in the elevation or run prompt).
- **SmartScreen** may show "Windows protected your PC" for a downloaded file it does not know. Whether it appears for a given download depends on Microsoft's reputation data and cannot be predicted. Signing alone would not remove it either; reputation builds up for a file and its certificate over time, and EV certificates no longer get a shortcut.
- **Smart App Control** (Windows 11, when switched on in enforcement mode) can block unsigned executables that it has no reputation for. Whether it is on is a per-device setting, and this was not tested on a device with it on. A valid signature can be used by Smart App Control in place of reputation, which is one real benefit of signing.
- Browsers and antivirus products may also warn about an unknown downloaded executable. No malware scan was run on these files, and this report makes no claim that they are free of malware.
- The installers' own behaviour is unchanged by signing or its absence: per-user install, no elevation requested (`requestedExecutionLevel: asInvoker`, `nsis.perMachine: false`).
- The 1.3.0 baseline ran on Windows 11 hardware; the 1.4.0 Preview and 1.5.0 builds were never run by the build tooling. The ARM64 installer has been checked only statically; no Windows on Arm device has run it.

Until signed, tell users plainly in the release notes that the installers are unsigned, how to verify the checksum, and what the Windows prompt will look like.

### 1.4 Exact owner steps

Pick one route. SignPath Foundation is the recommendation of [windows-signing.md](../platforms/windows-signing.md) (free, key stays in an HSM, publisher shown as "SignPath Foundation"); Certum Open Source Code Signing is the fallback (your own name as publisher, local signing).

**Route A: SignPath (CI)**

1. Apply at signpath.org with the GizeVerse/GizeCat repository; prepare the code signing policy page; turn on MFA for everyone with access.
2. In SignPath create the project, connect GitHub as the trusted build system, create a release signing policy with manual approval, and create a CI user with the submitter role and an API token.
3. Create the artifact configurations from `.github/signpath/` (`windows-installers.xml` always; `windows-app-helper.xml` only for the optional first round).
4. In GitHub, create the environment `windows-signing` with yourself as required reviewer before the first run; add the secret `SIGNPATH_API_TOKEN` and the variables listed in [release-automation.md](../platforms/release-automation.md). Use `gh secret set` without a value on the command line so the secret never reaches your shell history.
5. Bring `release.yml` with the `signpath` choice to a branch GitHub can start it from, run it with `windows_signing: signpath`, approve the environment, and approve each request in SignPath.
6. Download the signed installers and check them yourself with `scripts/verify-windows-signature.ps1`; read `signing-provenance-windows.txt`.
7. A signed build is a different file with a different checksum: rebuild the release's `SHA256SUMS.txt` from the files you actually publish (`npm run release:sums`).

**Route B: your own certificate (local)**

1. Buy or obtain a code-signing certificate whose key is on a token or cloud HSM that appears in the Windows certificate store, and install its client software.
2. List it: `Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert | Format-List Subject, Issuer, Thumbprint, NotAfter`.
3. Run `powershell -ExecutionPolicy Bypass -File scripts\sign-windows.ps1 -CertificateThumbprint <THUMBPRINT> -TimestampUrl <your CA's RFC 3161 URL>` (mode `SignExisting` signs copies of the installers; `-Mode Rebuild` rebuilds with every executable signed from a clean commit). Never paste a PIN or password into a chat, issue or log.
4. Verify with `scripts/verify-windows-signature.ps1`, then rebuild `SHA256SUMS.txt`.

After either route, say "signed by <subject>" only for what the verifier confirmed, and keep saying that signing does not guarantee SmartScreen or Smart App Control acceptance.

## 2. Android

### 2.1 Current state

| Output | State | Source of that state |
|---|---|---|
| Trial APK `GizeCat-1.5.0-android-trial-debugsigned.apk` | Signed with the Android **debug** certificate. Application id `io.github.gizeverse.gizecat.trial`, label "GizeCat (trial)". For sideload trials only, never for distribution | `android/app/build.gradle.kts`: build type `trial` (`applicationIdSuffix = ".trial"`, `signingConfig = signingConfigs.getByName("debug")`) |
| Release APK `GizeCat-1.5.0-android-unsigned.apk` | **Unsigned.** Android refuses to install an unsigned APK | Build type `release` takes `signingConfigs.findByName("release")`, which exists only when a key is configured |
| Release AAB `GizeCat-1.5.0-android-unsigned.aab` | **Unsigned.** Google Play does not accept it | Same |
| Production keystore | **Does not exist** | Nothing configures one |

Versions: `android/version.properties` has `versionName=1.5.0` and `versionCode=10500` (MAJOR*10000 + MINOR*100 + PATCH; the Gradle build refuses a code lower than `package.json`'s formula gives). The release application id is `io.github.gizeverse.gizecat`, frozen in `src/shared/identity.ts`.

How the build chooses a key (`android/app/build.gradle.kts`): the first source that holds anything wins.

1. The environment: `ANDROID_KEYSTORE_FILE`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. A blank value counts as unset.
2. `android/keystore.properties` (gitignored; template `android/keystore.properties.example`) with `storeFile`, `storePassword`, `keyAlias`, `keyPassword`.
3. Nothing: unsigned release outputs.

A partial source stops the build and names what is missing, never a value. The keystore file must exist or the build stops. `.gitignore` lists `android/keystore.properties`, `*.jks` and `*.keystore` as a second line of defence.

Related, statically visible: the Android app still requests exactly four permissions (`SYSTEM_ALERT_WINDOW`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE`, `POST_NOTIFICATIONS`; the manifest's other `uses-permission` entry carries `tools:node="remove"`, which strips a permission that `androidx.core` would otherwise add, so it is not a request). Signing does not change that. See [android-signing.md](../platforms/android-signing.md) for the full procedure.

### 2.2 Secure keystore creation workflow

The owner does this; no agent creates, handles or asks for a key. Everything in angle brackets is a placeholder for your own value. Never put a real password, keystore or alias in the repository, an issue, a chat or a log.

1. **Decide the Play relationship first** (hard to change after the first upload). Play App Signing with an **upload key** is recommended: your key proves an upload came from you, and Google signs what users install. Whether you also supply Google your own app signing key (so the GitHub APK and the Play install share one certificate) is the choice described in [android-signing.md, section 2](../platforms/android-signing.md#2-decide-how-play-and-the-github-apk-relate).
2. **Create the keystore outside the repository**, in a folder only you can read. Either run `scripts/android-create-upload-key.ps1` (it refuses to run if the keystore exists and refuses a folder inside the repository; keytool asks for the password itself) or run keytool by hand. Command shape, placeholders only:

   ```text
   keytool -genkeypair -v -storetype PKCS12 -keystore <KEYSTORE_PATH_OUTSIDE_THE_REPO>/<KEYSTORE_NAME>.jks -alias <KEY_ALIAS> -keyalg RSA -keysize 4096 -validity 10000
   ```

   - Do not pass a password on the command line; keytool prompts for it, so it stays out of your shell history.
   - The certificate carries the name and organisation you type: use details you are willing to publish.
   - `-validity 10000` is about 27 years; Google Play requires the certificate to be valid beyond 22 October 2033.
   - With PKCS12 the key password equals the keystore password.
3. **Record the certificate's SHA-256 fingerprint** (public): `keytool -list -v -keystore <KEYSTORE_PATH> -alias <KEY_ALIAS>`. It is how you tell keys apart later.
4. **Back it up in two places.** At least two copies on separate encrypted offline media kept in different locations, passwords in a password manager and not stored with the media. Test each copy with the `keytool -list` command. A GitHub secret cannot be read back, so it is not a backup.
5. **Point the build at it**, either with the four variables for one shell session, or with `android/keystore.properties`:

   ```properties
   storeFile=<KEYSTORE_PATH_WITH_FORWARD_SLASHES>
   storePassword=<KEYSTORE_PASSWORD>
   keyAlias=<KEY_ALIAS>
   keyPassword=<KEY_PASSWORD>
   ```

   - Forward slashes in `storeFile` (a backslash is an escape in a Java properties file).
   - If you use the variables, read the password without echo; the environment wins over the file.
6. **Build**: `npm run android:release` (APK and AAB), or `npm run android:apk` / `npm run android:aab` for one. The outputs lose the `-unsigned` part of their names when a key was picked up. These commands run Gradle and need the Android SDK; they do not run tests.
7. **Verify the signature yourself** with `apksigner verify --print-certs` (APK) and `jarsigner -verify -verbose -certs` (AAB). The certificate's SHA-256 must be the fingerprint from step 3, and must not be the Android debug certificate.
8. **Upload the AAB to Play** (internal testing track first). Play only ever receives the public certificate or, for the app-signing-key choice, the key encrypted by Google's export tool; never upload the keystore.

CI route (optional): a GitHub environment `android-signing` with a required reviewer and the four secrets, used by `.github/workflows/android-release.yml` (`signing: release-signed`). It refuses debug-signed outputs and an APK and AAB signed by different certificates. It has never been started.

If the key is lost or exposed, see [android-signing.md, section 9](../platforms/android-signing.md#9-if-a-key-is-lost-or-exposed). The short version: an upload key can be reset through the Play Console; a key that signs APKs outside Play cannot be recovered, and users would have to uninstall.

### 2.3 Upgrade compatibility warning

Android accepts an update only when the new APK has the same application id and the same signing certificate as the installed one.

- A production-signed GizeCat **cannot update** the debug-signed trial. They differ in certificate and also in application id (`io.github.gizeverse.gizecat` against `io.github.gizeverse.gizecat.trial`), so Android treats them as two separate apps, each with its own cat and settings. Installing the production app does not touch the trial, and the trial does not become the production app.
- What a person using the trial must do to move over: in the trial, save the cat to a file (Settings, "Take your cat to another device"); install the production app; load the file there; then uninstall the trial. They end up with two floating cats if both stay installed.
- The same applies later between two production channels with different certificates (for example a GitHub APK signed with your key and a Play install signed by Google's app signing key): Android refuses the in-place update, and the user must save the cat, uninstall, install the other one and load the file. Choosing to supply your own app signing key to Play avoids this ([android-signing.md](../platforms/android-signing.md#2-decide-how-play-and-the-github-apk-relate)).
- The trial's `versionCode` is `10500` for the 1.5.0 build (plus the preview number only for preview builds). A later production release must keep a `versionCode` that is never lower than any earlier one and is never reused.
- Do not rotate or replace a production key after release unless you accept that users must uninstall. Android certificates are not renewed.

### 2.4 Exact owner actions

1. Decide the Play App Signing option (section 2.2, step 1).
2. Create the upload keystore outside the repository (step 2) and record its SHA-256 fingerprint (step 3).
3. Make two encrypted offline backups and test them (step 4).
4. Configure the build with the four variables or `android/keystore.properties` (step 5).
5. Run `npm run android:release`, confirm the output names no longer end in `-unsigned`, and verify both signatures (steps 6 and 7).
6. Install the signed APK on a phone or tablet you own and run it before you distribute it. Nothing in 1.5.0 has been run; this step is what would turn "signed" into "tested".
7. Create the Play Console app, upload the AAB to internal testing, and complete the store forms ([docs/store/google-play/release-readiness.md](../store/google-play/release-readiness.md)).
8. Rebuild `release/1.5.0/SHA256SUMS.txt` from the files you actually publish (`npm run release:sums`). Do not attach the debug-signed trial APK as a release.

## 3. What this report does not claim

- No verified publisher, SmartScreen trust, Smart App Control acceptance, Play approval or malware-free status for any 1.5.0 file.
- No signing route was exercised. Every signed-result statement is untested until real credentials exist.
- No hash or size is recorded here; the checksums belong to the files the owner actually publishes.
- macOS and iPad are not part of this release candidate; the 1.4.0 Preview documents about them are unchanged ([macos-signing.md](../platforms/macos-signing.md)).
