# GizeCat 1.5.0 release candidate: artifact inventory and static verification

This is the evidence record for the final 1.5.0 release-candidate build: what was built, from exactly which source commit, how it was inspected, and what was **not** verified. Nothing here is published, tagged or attached to a GitHub Release, and no tag or release was created.

**Verification level, stated plainly.** Every artifact below is **COMPILED_OR_PACKAGED** and **statically verified** (type-check, lint, read-only adversarial code reviews, and static inspection of the built files). **Nothing in 1.5.0 was run by anyone**: no automated test, no emulator or simulator, no application launch, no installer run, no device. The only runtime evidence in this project for the floating cat is the owner's real-phone check of **1.4.2** on one Android phone, which predates all of the Living Companion code.

**The documentation commit that records this inventory** (the branch head after `431b8c6`) differs from `431b8c6` only under `docs/`. That was checked by comparing the git tree hashes of every path that can enter an artifact (`src`, `android`, `scripts`, `build`, `package.json`, `package-lock.json`, `electron-builder.yml`, `THIRD_PARTY_NOTICES.md`, `LICENSE` and the three tsconfig files): all identical. A commit cannot contain its own hash or the hashes of a build that preceded it, so this record names the source commit the artifacts were built from, not the commit that holds this file.

**How this build came to be (an honest account).**
1. An earlier 1.5.0 build was made from `f8fe919`. Later, `597d2e2` (documentation only) was committed, and the first report named `f8fe919` as the build commit and `597d2e2` as HEAD. The git tree hashes of every artifact-relevant path were identical between `f8fe919` and `597d2e2`, so those artifacts already matched that source. They were nevertheless **superseded**: the four reported minor issues were then resolved in source (`538aed0`) and everything was rebuilt.
2. The superseded artifacts and their `SHA256SUMS.txt` were set aside (`release/1.5.0.superseded-f8fe919/`, git-ignored) and **no hash from them is reused**; none of the five new hashes equals an old one.
3. The first rebuild runner was interrupted (the session restarted) after the Windows step finished and while the Android step was waiting for the machine lock held by another project's job. The Windows installers in this record were built in that first run; the Android steps and the checksum file were produced by a resumed run from the same commit, after re-checking that HEAD and the tree had not changed. No process of this build was left running.

The AAB contains `base/assets/main.js` (the same bundle, with `watchFirst`), `base/manifest/AndroidManifest.xml` and `BundleConfig.pb`, 52 entries and no `lib/` entries; its manifest is protobuf-encoded, so its permission list was not parsed separately (it comes from the same manifest merge as the APKs').

**Windows (`scripts/check-win-payload.mjs`, which reads file headers and never runs a binary).** Both `win-unpacked` (x64) and `win-arm64-unpacked` passed with no failures and no warnings: the executable's PE machine type matches the architecture (x64 and ARM64 respectively), the matching `koffi` native module is present and unpacked, the asar integrity resource and the fuse wire match `electron-builder.yml`, and the asar holds only the application (no sources, docs or old installers). Both `app.asar` files contain `watchFirst`, so both installers carry the final source's engine.

**Source (type-check and lint on the final source).** On the tree that became `538aed0`: `tsc -p tsconfig.node.json`, `tsc -p tsconfig.web.json` and `eslint src tests` all exit 0 (run by a detached runner under the machine lock). `431b8c6` changed documentation only.

**Reviews.** Two adversarial read-only reviews, each finding independently checked by a second reader: the first (before the original build) confirmed eight defects, all fixed in `5c3e2d4`; the second reviewed the reconciliation change and confirmed one defect (a test that did not expect the two new boolean temperament flags), fixed before `538aed0`. A review is not a test.

## What is NOT verified

- **No runtime evidence at all for 1.5.0.** The Living Companion code (events, props, personalities, mood, Laser Mode, journal, the new pages and panel, the Android stage window, the shy and lazy behaviour, the novelty factor) has never executed. Behaviour, drawing quality, animation feel, timing and battery use are UNVERIFIED.
- **No test was run, and verification by `node .claude/scripts/verify.mjs fast` was not performed**, because it runs the test suite, which the owner prohibited. The last passing run of that gate is from before this work and covers different code. The unit tests written for this release were never run; several expectations are hand-estimated (statistical bands, timing assumptions, pose margins) and may need adjusting when the owner's CI first runs the suite. Existing suites may also hold expectations that no longer hold; the reviews looked for these by reading.
- **Installers were never run, installed or upgraded.** The silent-install, upgrade-from-1.3.0 and uninstall behaviour of the 1.5.0 installers is not observed (the owner's real install is in use and the project rules forbid it).
- **Multi-monitor and mixed-DPI behaviour of props and the laser dot, the Windows laser dot over a real desktop, the Android 12+ pass-through of the wider non-touchable stage window at 0.8 opacity, and phone or tablet behaviour of the new panel** are all NOT RUN. The 1.4.2 owner verification covers one phone and none of this.
- **Tablets, other Android phones, Windows 10 and Windows on Arm hardware** have not been individually tested (the ARM64 installer was built on an x64 PC).
- **No claim** is made of SmartScreen trust, a verified publisher, Google Play approval, or that the app is free of malware (a static review does not prove that).

## If you rebuild

Any change to the sources invalidates the hashes: rebuild from a clean committed tree, run `npm run release:sums`, and refresh the table in [the release-notes draft](1.5.0-release-candidate.md) and this record.
