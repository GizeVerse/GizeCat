# GizeCat 1.4.0 (release candidate): one cat, more devices

> **Draft, not published.** GizeCat 1.3.0 stays the current release until the owner approves 1.4.0. The files and checksums below are those of the candidate build made on 2026-11-10 from commit `d3cdb6b` on the branch `release/1.4.0-universal-devices` (later commits change documentation only). A rebuild gives different checksums.

GizeCat is a small cat that lives on your screen and never gets in the way of your clicks. It is the first character of **GizeVerse**: free, open source and MIT-licensed.

1.4.0 brings the same cat to Windows on Arm PCs, Intel and Apple Silicon Macs, iPads and Android tablets. **This is a candidate. Nothing in 1.4.0 has run on any device yet:** no tests, emulators, simulators, CI test workflows or physical-device checks were run for it. The files below were compiled or packaged and then inspected statically; a build is not a test. Please tell us what happens on your device (see "Feedback").

## What's new

**Windows**
- One installer per architecture: `-x64` for almost every PC, `-arm64` for a Windows on Arm PC (Settings → System → About → System type). The ARM64 installer stops with a clear message on a PC that is not Windows on Arm.
- Same app identity as 1.3.0, so installing over 1.3.0 is designed to keep your cat (the 1.4.0 upgrade has not been run). The installer and shortcuts are still called "Desktop Cat".

**macOS (Intel and Apple Silicon)**
- The desktop cat on the floor of each screen, in a click-through panel that stays below menus and the Dock. No window climbing on macOS.
- A menu-bar icon (its click opens the menu), a Dock icon you can turn off, and an opt-in "Open at login" (from /Applications).
- No permission prompts: no Accessibility, Screen Recording, camera or microphone. Screen analysis is not available on macOS. Settings name macOS things in macOS terms.

**iPad**
- The installable web app: open it in Safari, then Share → **Add to Home Screen**. It works offline once installed, and the settings sheet says when it is ready offline. No App Store app; the cat lives inside its own window, because iPadOS lets no app draw over other apps.

**Android tablets**
- A native app with **no internet permission**, no cloud backup and a hardened WebView, showing the same cat as the web app. Android 10 or later. Back closes the settings sheet first and returns from the licences and privacy pages to the cat.
- The release APK and AAB become installable or uploadable once the owner signs them; the signing pipeline is ready.

**Every device**
- **Take your cat to another device:** save your cat to a file and load it elsewhere (Settings → Personality on Windows and macOS; the settings sheet on tablets). You see what a file would change before anything changes; nothing is uploaded; it is a copy, not a sync. A file never contains API keys, screen-analysis or AI settings, window titles or folder paths.
- In the web and Android app: a privacy statement and the third-party licences, both inside the app.

## Known limitations

- **Nothing has run on a device.** Not the 1.4.0 Windows installers, not the ARM64 build, not macOS, not the web app, not the Android app.
- **Unsigned or ad-hoc signed.** SmartScreen warns on Windows (Smart App Control may block); macOS blocks the ad-hoc apps until you allow them; the Android release files need the owner's key.
- **macOS is floor-only:** no window climbing, no fullscreen detection, no screen analysis. A Keychain prompt at launch from Chromium's own cookie encryption is not ruled out.
- **Tablets:** the cat lives inside its own window; Safari may clear a Safari tab's data after 7 days without a visit (install the web app to keep your cat); an outdated Android System WebView shows no cat.
- **Not tested** on Windows 10, multi-monitor or mixed-DPI hardware, or with real AI providers.

## What ran for this candidate

- Static checks on the final code: TypeScript (`tsconfig.node.json`, `tsconfig.web.json`) and ESLint over the whole repository: no errors.
- Builds from commit `d3cdb6b`: the Windows x64 and ARM64 installers; the macOS x64 and arm64 ad-hoc zips (in a disposable WSL 2 distro, `npm run package:mac:adhoc-wsl`); the web bundle and its zip; the Android release APK, AAB and trial APK (Gradle).
- Static inspections, never running anything: both Windows unpacked builds (`scripts/check-win-payload.mjs`: PE machine, only the right native binary, app.asar holding only the app, asar integrity, fuses); both macOS zips (`scripts/check-mac-payload.mjs`: thin, signed Mach-O files of the right architecture, bundle identity and version, app.asar holding only the app, no native module, asar integrity, fuses, framework symlinks); both Android APKs (`apkanalyzer`: no permissions, the right application IDs, versionCode 10400, minSdk 29, targetSdk 36, not debuggable, the web pages present).
- Two independent reviews of the 1.4.0 changes; their confirmed findings were fixed before this build.
- **No test suite, emulator, simulator, CI test workflow or physical device was used for 1.4.0.** No GitHub Actions workflow was started.

## Owner actions (only what needs the owner's access or credentials)

1. **Run the tests that were written and not run** (`node .claude/scripts/verify.mjs fast`, then `verify full` and `npm run test:web` on Windows) before any test claim is made, and decide whether to publish 1.4.0 (keep 1.3.0 as Latest until then; a pre-release is an option).
2. **Bring the candidate to `main`** when you approve it. GitHub starts a manual workflow only if its file is on the default branch: `macos-packages.yml`, `pages.yml` and `android-release.yml` need this; `release.yml` can already run from the candidate branch.
3. **iPad public address:** run `pages.yml` (the Pages source is already set to GitHub Actions). Only after its first successful run is `https://gizeverse.github.io/GizeCat/` live; check it on an iPad before telling anyone.
4. **macOS:** run `macos-packages.yml` with `signing: adhoc` for DMG and universal builds. For notarized builds: join the Apple Developer Program; create a Developer ID Application certificate and an App Store Connect API key; create the GitHub Environment `macos-signing` with yourself as required reviewer; add `MAC_CSC_LINK`, `MAC_CSC_KEY_PASSWORD`, `APPLE_API_KEY_P8_BASE64`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER` there (formats in [release-automation.md](../platforms/release-automation.md), steps in [macos-signing.md](../platforms/macos-signing.md)); run it with `signing: developer-id`.
5. **Android:** create the upload key yourself ([android-signing.md](../platforms/android-signing.md)) and either sign locally (`npm run android:release` with `android/keystore.properties` or the `ANDROID_*` variables) or add `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` to the GitHub Environment `android-signing` and run `android-release.yml`. For Google Play: a developer account, developer verification, Play App Signing, the listing and data-safety answers in [docs/store/google-play](../store/google-play/), and a privacy policy address of your choice (for example the hosted `privacy.html` once Pages is live).
6. **Windows (optional):** apply to SignPath Foundation and run `release.yml` with `windows_signing: signpath` (GitHub Environment `windows-signing`), or buy a certificate and sign locally with `scripts/sign-windows.ps1` ([Windows signing](../platforms/windows-signing.md), [all owner steps](../platforms/release-owner-actions.md)).
7. **Publish the draft release** yourself when ready; attach any signed builds first and regenerate `SHA256SUMS.txt` for the final set (`npm run release:sums`).
8. **Collect real-device reports** (Windows on Arm, Macs, iPads, Android tablets, Windows 10) and bring them to the next session.
